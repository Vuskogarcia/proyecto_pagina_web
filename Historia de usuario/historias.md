# Backlog Priorizado

*Ordenado por dependencia técnica: primero la base (autenticación, catálogo, compra), luego el soporte postventa (tickets), que es el problema central del proyecto (ver `vision-producto.md` §1 y `problema-duro.md`).*

| Prioridad | Historia de usuario | Criterios de aceptación verificables |
| --- | --- | --- |
| **1** | **Como usuario, quiero registrarme e iniciar sesión con un rol definido (cliente, agente o administrador) para acceder a las funciones correspondientes a mi rol.** | 1. El usuario puede registrarse con email y contraseña.<br>2. El sistema asigna un rol al usuario (cliente por defecto; agente/administrador asignado por un administrador).<br>3. Al iniciar sesión, el usuario solo ve las opciones permitidas para su rol.<br>4. Un usuario no autenticado no puede acceder a rutas protegidas. |
| **2** | **Como cliente, quiero consultar el catálogo de productos para conocer los productos disponibles antes de realizar una compra.** | 1. El sistema muestra los productos disponibles.<br>2. Cada producto muestra nombre, precio y descripción.<br>3. El cliente puede consultar el detalle de un producto.<br>4. Los productos sin disponibilidad se identifican como agotados. |
| **3** | **Como administrador, quiero gestionar el catálogo y el inventario para mantener actualizada la información de los productos disponibles.** | 1. El administrador puede crear productos.<br>2. Puede modificar nombre, descripción, precio y cantidad disponible.<br>3. Puede desactivar productos.<br>4. Los cambios realizados se reflejan en el catálogo de la tienda. |
| **4** | **Como cliente, quiero agregar productos a un carrito y realizar el checkout para completar mi compra.** | 1. El cliente puede agregar y eliminar productos del carrito.<br>2. El sistema calcula correctamente el total.<br>3. El cliente debe ingresar la información necesaria para realizar el pedido.<br>4. Al finalizar, el sistema genera un pedido con un identificador único (formato `PED-00001` o UUID). |
| **5** | **Como cliente, quiero crear un ticket de soporte asociado a uno de mis pedidos para reportar una duda, reclamo o problema con mi compra.** | 1. El cliente puede seleccionar uno de sus pedidos.<br>2. Puede ingresar asunto y descripción del problema.<br>3. El sistema genera un número único de ticket (formato `TCK-00001` o UUID).<br>4. El ticket queda asociado al pedido seleccionado. |
| **6** | **Como cliente, quiero consultar el estado de mis tickets para conocer el avance de mi solicitud.** | 1. El cliente puede visualizar sus tickets.<br>2. Cada ticket muestra número, fecha, asunto y pedido asociado.<br>3. El sistema muestra el estado: Abierto, En proceso, Resuelto o Cerrado.<br>4. El estado se actualiza cuando el agente realiza cambios. |
| **7** | **Como agente de servicio al cliente, quiero visualizar una cola de tickets sin asignar para elegir cuáles atender.** | 1. El agente puede visualizar los tickets sin asignar.<br>2. Cada ticket muestra el cliente y pedido asociado.<br>3. Los tickets pueden ordenarse por fecha o estado.<br>4. Un ticket ya asignado no aparece en la cola de "sin asignar". |
| **8** | **Como agente de servicio al cliente, quiero tomar (asignarme) un ticket de la cola para atenderlo, incluso si otro agente intenta tomarlo al mismo tiempo, para evitar que dos agentes atiendan el mismo caso.** | 1. Al tomar un ticket sin asignar, este queda asignado únicamente al agente que hizo la solicitud.<br>2. Si dos agentes intentan tomar el mismo ticket en simultáneo, solo uno obtiene la asignación; el otro recibe un mensaje indicando que el ticket ya fue tomado.<br>3. Existe una prueba automatizada que simula la asignación concurrente y verifica que nunca queda asignado a más de un agente (ver `problema-duro.md` §3).<br>4. Cada asignación exitosa queda registrada con agente, ticket y fecha/hora. |
| **9** | **Como agente de servicio al cliente, quiero consultar la información del pedido asociado a un ticket para conocer qué compró el cliente antes de atender su solicitud.** | 1. Desde el ticket se puede acceder al pedido relacionado.<br>2. Se muestran los productos del pedido.<br>3. Se muestra la fecha y estado del pedido.<br>4. La información mostrada corresponde al pedido seleccionado por el cliente. |
| **10** | **Como agente de servicio al cliente, quiero responder los tickets que tengo asignados y cambiar su estado para registrar el proceso de atención.** | 1. El agente solo puede responder tickets que tiene asignados.<br>2. La respuesta queda registrada en el ticket con fecha y autor.<br>3. El agente puede cambiar el estado del ticket (Abierto → En proceso → Resuelto → Cerrado).<br>4. El cliente puede visualizar la respuesta y el nuevo estado. |

## Notas de la revisión

- **Se agregó la historia 1** (autenticación con roles): todas las demás historias asumen un usuario identificado con un rol; sin ella el resto no es implementable de forma verificable.
- **Se reordenó por dependencia técnica:** login → catálogo → carrito/checkout → tickets → asignación → resolución. Un ticket requiere un pedido existente, así que catálogo/compra debe ir antes.
- **Se dividió la historia original 3** ("visualizar cola de tickets") en dos: **7** (ver cola sin asignar) y **8** (tomar un ticket con control de concurrencia). Esto separa claramente el problema duro declarado en `problema-duro.md` como su propia historia, con su propio criterio de aceptación verificable — que es justo lo que exige la evidencia del proyecto.
- **Historia 10** (antes 5): se acotó el criterio 1 para que un agente solo pueda responder tickets que tiene asignados, evitando que dos agentes editen el mismo ticket sin control (refuerza la coherencia con el problema duro).
